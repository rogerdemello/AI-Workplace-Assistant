A. Sentiment & signals (core product)
   [x] Every employee chat path persists the sentiment pipeline. Both the
       synchronous and the deferred path are now instrumented — the deferred
       one is the production default (CHAT_DEFER_NONBLOCKING_SIDE_EFFECTS), so
       instrumenting only the sync path would have left failures invisible.
   [ ] Verify in staging under real traffic. Not done — needs an environment.
   [x] Backfill/reconcile: scripts/reconcile_sentiment.py finds user messages
       with no sentiment log and reprocesses them. Safe to re-run — writes are
       idempotent now (application guard plus a partial unique index on
       sentiment_logs.message_id), so a replay cannot double-count and skew a
       score. Doubles as the replay path for anything that shows up in
       sentiment_pipeline_failures_total; previously a failed write lost the
       signal permanently while the message itself was saved.
       Checked against production: 0 user messages in the last 30 days, so
       there is currently nothing to repair there.
   [ ] HR dashboard smoke test after real chat traffic: confirm sentiment_score,
       trend, risk and top_emotion move. Covered by integration tests, not by
       an observed staging run.

A2. Composer dropping sends — ROOT CAUSE FOUND AND FIXED
   [x] The real cause was never in ChatPanel: ChatContext.send had a 500ms
       debounce that returned early and discarded the message. The composer had
       already cleared the input by then, so the employee saw an empty box and
       assumed it had sent. It only bites when turns arrive within 500ms of
       each other, which is exactly why it reproduced in CI and never locally.
       The debounce now waits out the remainder instead of discarding.
   [ ] Queueing turns typed during an in-flight reply is still not implemented.
       Sends are refused visibly (text stays in the composer). Three attempts
       at a queue regressed — worth doing properly, but it was never the cause
       of the failures it was written to fix.

   Lesson for this area, recorded because it cost most of a session: three
   diagnoses were wrong because each was a hypothesis patched blind. What
   settled it was reading the CI server log and counting POSTs per
   conversation, then following the accepted-but-never-sent gap into
   ChatContext. Get the evidence first here; the timing only reproduces on CI.

A2b. Composer dropping sends SILENTLY — FIXED
   [x] The harm was the silence, not the refusal: a send during an in-flight
       reply cleared the input and dropped the message, so the employee saw an
       empty box and assumed it had gone. The input now clears only on the path
       that actually dispatches, so a refused send leaves the text visible.
       The button also no longer disables on transient isSending/isTyping, so
       it cannot flip disabled between a press and the click dispatching.
       Covered by new-frontend/e2e/composer.spec.ts, which asserts a second
       message typed during a reply is either sent or still in the box.

2. HOW TO DO IT (practical steps)
--------------------------------------------------------------------------------

Deploying (changed — read this)
   1. `cd backend && alembic upgrade head`. Required now; the app will not
      create Postgres tables for you.
   2. Watch the boot log for schema_audit. An error there means step 1 was
      skipped or a migration is pending.
   3. DB_CREATE_ALL=true forces the old behaviour, for throwaway envs only.

Sentiment pipeline (wired in code — operationalize it)
   1. Deploy backend with latest chat.py pipeline helper.
   2. Run integration tests: pytest backend/tests/test_chat_sentiment_hr.py
   3. Manual: employee sends chat → HR refreshes Pulse/Employees → scores move.
   4. Watch /metrics: sentiment_pipeline_failures_total should stay flat.

HR dashboard verification
   1. Log in as HR → GET /api/v1/analytics/dashboard (or use UI).
   2. Cross-check one employee: SentimentLog rows vs dashboard sentiment_score.
   3. Document any delay (caching, refresh interval).

Load testing
   python -m scripts.loadtest --base-url https://staging.example.com \
       --employees 25 --hr 5 --duration 60
   Run against staging. Compare p95 against whatever you decide is acceptable
   for the chat hot path; there is no agreed budget yet — set one.

Browser e2e (needs both servers up; see playwright.config.ts header)
   cd new-frontend && npm run test:e2e

Safe rollout
   1. Feature flag optional: “strict_pipeline” logging only before full enforce.
   2. Staging → canary → full prod; watch error rate on SentimentPipelineService.

3. HOW TO MAKE IT WORLD CLASS
--------------------------------------------------------------------------------

Accuracy & fairness
   - Move beyond lexicon-only: add a managed model (Azure/OpenAI/other) with
     fallback to rules; evaluate on labeled in-domain data. (Hybrid LLM +
     lexicon fallback exists — SENTIMENT_HYBRID_ENABLED — but has not been
     evaluated against labeled in-domain data.)
   - Multilingual support; test for bias across regions and roles. Not started.

Reliability
   - Idempotent pipeline writes; dead-letter queue for failed processing;
     replay jobs. Not started — failures are now counted and logged, but a
     failed message is still lost rather than retried.

Privacy & compliance
   - Minimize stored raw text; prefer aggregates; clear retention; DPIA-ready
     documentation; role-based redaction in HR UI. Not started. Note that
     proactive nudges now persist to chat history, which adds to the retention
     surface — worth including in that policy.

Explainability
   - HR sees “why” (factors: recent negative ratio, topics, emotion mix) not
     only a single number.

Human in the loop
   - Escalation workflows (HR review, manager coaching) tied to signals, not
     auto-disciplinary use of scores.

Performance
   - Sub-second chat; async pipeline if needed; precomputed dashboard tiles.
     No agreed latency budget exists yet — set one before the load test, or
     the numbers have nothing to fail against.

   - Hybrid sentiment: API + lexicon fallback; calibration to 0–100 scale.

   - Rule engine + notifications (email/Slack/Teams) with suppression/cooldowns.
   - Optional HR case/ticket creation from high-risk patterns.

Phase 4 — Scale & enterprise (6–12 months)
   - Multi-tenant, regional data residency, SSO, audit trails.
   - Formal model governance: versioning, A/B evaluation, fairness reviews.
