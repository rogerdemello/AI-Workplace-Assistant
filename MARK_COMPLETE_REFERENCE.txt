PART I — WHAT MARK IS
================================================================================

MARK is an AI-powered HR + workplace operating system. It is designed to replace
or absorb: HR portals, forms, helpdesk tools, surveys, and manual HR workflows.

Core loop (target experience):
  Conversation → Action → Intelligence → Automation

One-line definitions (use externally):
  • "Talk to Mark — everything HR gets handled, and HR gets real-time insight."
  • MARK turns everyday employee conversations into actions, insights, and
    proactive HR decisions.

Who uses it:
  • Employees talk; MARK understands and acts.
  • HR gets insights, alerts, and operational control.

What MARK is NOT (positioning guardrails):
  • Not "just a chatbot" or a one-off survey tool.
  • Not only classic HR software — emphasis on continuous listening + early action.

Problems MARK targets:
  1) HR often learns how people feel too late.
  2) Employees stay silent → silent attrition.
  3) HR time sinks into repetitive tasks.

MARK is framed as a prevention / early-intervention system, not only reporting.

PART III — FEATURE BLUEPRINT (DETAIL)
================================================================================

--- 1. Chat experience (frontend core) ---

Required:
  • Chat widget: bottom-right, floating, expandable panel.
  • Persists across pages; minimized state should retain context.
  • Streaming responses; typing indicators; quick replies where appropriate.
  • Attachments: documents, screenshots (full pipeline, not text-only mention).
  • Chat history.
  • Behavior: one question at a time where possible; human tone; avoid forms
    unless necessary.

--- 2. Conversation engine (core logic) ---

Responsibilities:
  • Intent detection: complaint, leave, policy, reminder, emotional,
    productivity, lifestyle, etc.
  • Entity extraction: dates, names, reasons, topics.
  • Slot filling: ask missing info, skip known info, enforce order.
  • Context: remember conversation, handle switching, resume flows.
  • State machine style tracking, e.g. intent + step + collected data.

--- 3. Multi-agent system ---

Agents (conceptual split; not one monolithic bot):
  • HR agent — complaints, leave, HR workflows.
  • Productivity agent — meetings, emails, reminders.
  • Life assistant — food, weather, daily suggestions.
  • Analysis agent — sentiment, risk, behavior patterns.
  • Emotional agent — stress support, empathy.
  • Proactive agent — nudges, follow-ups.

--- 4. HR workflows ---

Complaint system (target flow):
  Detect issue → collect context → person involved → anonymity → confirm →
  create ticket. Features: auto-priority, duplicate detection, SLA, escalation,
  assignment.

Leave system:
  Start/end dates → leave type → reason → validation → confirmation.
  Features: approval workflow, status tracking, HR dashboard sync.

HR helpdesk:
  Queries → tickets; category detection; SLA.

--- 5. Intelligence engine (USP) ---

Per message: sentiment (e.g. 0–100 scale in product language), emotion (stress,
frustration, …), topic (manager, salary, …), severity.

Aggregate per employee: sentiment score, engagement score, risk score,
mental-health-style composite (as implemented responsibly, not clinical).

Derived: attrition risk signals, burnout patterns, manager effectiveness (where
data supports it).

--- 6. Proactive engine (differentiator) ---

Trigger types (target):
  • Time-based — lunch, break, check-ins.
  • Behavior-based — inactivity, silent employee.
  • Emotional — low sentiment, repeated stress.
  • Health — illness follow-up, medicine reminders (policy/compliance sensitive).
  • Event-based — onboarding, manager change, appraisal, exit (high priority).

--- 7. Knowledge system (RAG) ---

Document upload, semantic search, contextual answers. Fallback: no raw errors;
graceful user-facing response.

--- 8. HR dashboard (control center) ---

Metrics: engagement, sentiment trends, attrition risk, eNPS-style proxy.
Alerts: high-risk employees, sentiment drops, repeated complaints.
AI insights: patterns, recommendations.
Employee table: sentiment, risk, last activity.
Visuals: line charts, department breakdown, risk heatmap (as designed).

--- 9. Ticket management (HR side) ---

Issue summary, priority with reason, SLA, assigned HR.
Advanced: AI insights, suggested actions, conversation history, tags,
duplicate detection.

--- 10. Employee dashboard (minimal target) ---

My tickets, my leave, my reminders, mood snapshot.

--- 11. Reminder system ---

Types: work, health, recurring habits.

--- 12. Integrations (target) ---

HR systems, employee directory data, payroll, leave balance.
Productivity: calendar, meeting rooms.
External: WhatsApp API, maps, weather (as product allows).

--- 13. WhatsApp integration ---

Full chat support, notifications, reminders (with provider + compliance).

--- 14. Emotional support ---

Detect stress; empathetic response; follow-up; escalate only when appropriate
(not a substitute for professional care).

--- 15. Event-based intelligence ---

Example: manager change → check-in message: "How's it been working with your
new manager?"

--- 16. Analytics pipeline (target path) ---

Message → sentiment → store → aggregate → patterns → insights → dashboard.

--- 17. Automation engine ---

Auto ticket creation, escalation, reminders, HR alerts, onboarding workflows.

--- 18. UX principles ---

Human, calm, minimal, non-robotic. Reduce forms and clutter.

--- 19. System requirements ---

Graceful errors, duplicate-action prevention, data consistency, performance.

--- 20. Final system flow (conceptual) ---

User message
  → Conversation engine
  → Agent selection (when multi-agent is on)
  → Workflow execution
  → Sentiment / analysis
  → DB update
  → Dashboard update
  → Proactive triggers

PART IV — GO-TO-MARKET & POSITIONING
================================================================================

Positioning — say this, not generic "AI HR chatbot":
  MARK is an AI HR partner that continuously listens to employees and helps HR
  act before problems escalate.

Avoid competing only on surveys/dashboards; compete on conversation + proactive
+ real-time intelligence. Edge narrative: MARK lives with the employee daily vs
periodic pulses.

Ideal customer profile (phase 1):
  • Roughly 50–300 employees; tech/SaaS; remote/hybrid; faster decisions;
    limited HR bandwidth.

Core pains to sell (not feature lists):
  1) HR doesn't know how people feel until too late.
  2) Employees don't raise issues → silent attrition.
  3) HR burns time on repetition.

Entry motion:
  Lead with killer slice: AI listening + sentiment + alerts ("detect issues
  before resignation").

Sales motion:
  Demo-first: real chat + complaint flow + dashboard alert.
  Problem pitch: "What if you knew team problems before they resigned?"
  ROI: tie to cost of regrettable attrition.

Pilot (suggested):
  2–4 weeks; integrate MARK; track sentiment, engagement, tickets; aim for
  visible insights within ~2 weeks.

Metrics to show HR:
  Attrition risk, sentiment trend, engagement, issue patterns; before/after.

Pricing sketch (Indian context from your notes):
  Per employee / month tiers (Starter: chat+tickets+basic sentiment; Growth:
  analytics + proactive + dashboard; Enterprise: integrations + custom).

Channels:
  LinkedIn content, cold outreach to HR heads/founders, demo videos,
  communities. Start direct + warm intros.

Demo script climax:
  Employee chats → complaint → sentiment drops → HR dashboard alert →
  "This is what your HR team doesn't see today."

Biggest mistake:
  Leading with "we have AI, chatbot, sentiment…" instead of outcomes:
  "We help you detect and fix employee problems early."

Launch plan sketch:
  Weeks 1–2 polish + fix flows; week 3–4 pilots; month 2 scale outreach.

KNOWN ISSUES
------------
Dual frontends
  • new-frontend appears primary; frontend/ diverges risk.

Database / migrations
  • Placeholder DATABASE_URL breaks Alembic until real URL supplied.
  • Migration vs live DB mismatch possible (duplicate tables, missing columns
    such as sentiment_logs.analysis_source, sentiment_logs.conversation_id,
    ticket_messages.is_internal; userrole enum may lack manager).

Redis
  • Defaults localhost:6379; if down, caching no-ops silently.

Azure OpenAI
  • Intent classifier + replies use chat_completion; retries use exponential
    backoff → extra seconds on errors.
  • Production must configure real credentials (defaults are mock placeholders).

Auth / conversation
  • Stale JWT or DB reseed causes missing conversation; client retries and
    starts new conversation; slow backend still yields timeouts.

Analytics
  • Some endpoints heavy on remote Postgres — tens of seconds; smoke scripts may
    need SMOKE_HTTP_TIMEOUT_SEC lifted.

Graceful degradation
  • Recent code paths attempt fallbacks on schema drift for sentiment_logs and
    ticket_messages; analytics may still degrade until DB aligned.


WHY CHAT IS SLOW (ROOT CAUSES)
------------------------------
Typical new-frontend path: POST .../conversations/{id}/respond/stream

  1. Intent classification: LLM call per message (IntentClassifier.classify via
     ai_client.chat_completion), unless mocked in tests.

  2. SmartChatService + orchestrator: extra LLM for replies; optional MARK
     intelligence snapshot when ENABLE_MARK_INTELLIGENCE_PIPELINE is true AND
     CHAT_SKIP_INTELLIGENCE_SNAPSHOT is false (defaults often skip snapshot to
     save one model call).

  3. Flow intents (leave, ticket, reminder, …): stream endpoint frequently runs
     full _process_conversation_message first, then SSE "streams" word-by-word.
     Time-to-first-visible-token ≈ entire generation + DB, not true streaming.

  4. Non-flow intents: Azure stream can still wait on first token; server
     CHAT_STREAM_TIMEOUT_MS (order of ~12s) may fall back to buffered path.

  5. Persistence: save messages + sentiment pipeline commits; partial deferral
     via CHAT_DEFER_NONBLOCKING_SIDE_EFFECTS but pipeline still costly.

  6. Network: cloud Postgres + Azure latency each turn; Redis absent → no cache.

  7. Frontend: auth verify may hit /auth/me; stream abort after
     VITE_CHAT_STREAM_TIMEOUT_MS (often ~120s) shows timeout copy.


INCOMPLETE OR FRAGILE WORKFLOWS
-------------------------------
  • Leave: chat flow OK; approvals, notifications, calendar, org rules need
    hardening vs blueprint.
  • Ticket/complaint: core flow OK; HR triage depth, escalation rules, real file
    attachments from chat incomplete (attachment is text metadata today).
  • Reminders: verify scheduler + delivery channels end-to-end.
  • Policy/RAG: depends on ingestion + embeddings config.
  • Proactive/event-based: hooks exist; not full breadth of blueprint events.
  • Surveys/wellbeing/billing/admin: routes exist — production completeness needs QA.
